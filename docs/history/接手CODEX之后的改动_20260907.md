## 一、代码改动（`scripts/src/vx.py`）

### 1. 补回格式选择器的中间层

Codex 把选择器收成两层（直连+限高 / 任意协议+限高）。漏洞是：
一条视频若只有超过上限的直连轨 + 不超上限的 m3u8 轨，会选中 m3u8——
在开着 Surge 的机器上分片必挂。

改成四层：**直连+限高 → 直连不限高 → 任意+限高 → 全兜底**。
原则是**协议可靠性优先于画质上限**：宁可要 4K 直连（只是文件大），
也不要 1080p 分片（下不下来）。

### 2. YouTube cookie 双向兜底（本轮最重要）

09-06 下午：**带** cookie → `Requested format is not available`
09-07 凌晨：**不带** cookie → `Sign in to confirm you're not a bot`

同一台机器、同一条链接，相隔几小时。这不是回归，是平台按 IP 信誉动态收紧。
**所以 `needs_cookies()` 的默认值怎么设都会有一半时间是错的。**

原来只有一个方向的兜底（我 09-06 写的），现在补齐另一个方向：

| 症状 | 动作 |
|---|---|
| 带 cookie 报 format is not available | 去掉 cookie 重试 |
| 不带 cookie 撞机器人校验 | `force_cookies=True` 强行带上重试 |

成功那次的姿势要跟着走完全程：新增 `force_cookies` 参数，
经 `_vx_force_cookies` 一路传给 `ensure_subs()` 和 `download()`，
否则 `ytdlp_base()` 里的 `needs_cookies()` 会在下一步把 cookie 又剥掉。

`download()` 是流式跑的、拿不到 stderr，所以没法按报错内容判断，
改成**失败后换一次姿势重来**，判断依据是第一次实际带没带 cookie
（`force_cookies or needs_cookies(url)`），不是看入参——
非 YouTube 站点 `needs_cookies()` 本来就返回 True，翻转前后一样，那样白跑一次。

识别串有坑：**YouTube 用的是弯引号 U+2019，直引号匹配不到**，两个都列了。

### 3. 新增 `--redownload`

`--force` 只忽略 `.done` 标记，主流程仍是「`find_media()` 非空就跳过下载」，
所以画质策略一变，老目录里那个文件永远换不掉。
实测：限高改好后重跑，拿到的还是昨晚那个 2160p VP9（173.8 MB，QuickTime 打不开）。

`--redownload` 把旧媒体挪进 `media/_replaced/` 再重下。
**挪而不删**——几百 MB 的东西删了找不回来，何时清由用户决定。

同时给 `--force` 加了一行提示：`! 媒体已在本地，--force 不会重下`，
帮助文本也改成明确说明。理由见下面第 4 条。

### 4. 平台级节流 `throttle()`

十五条批量实测：三条 YouTube 打完紧接两条 B站，
**第一条 B站 15/45/90 三档退避全用完（累计 150s）仍然 412**，靠缓存兜底；
紧随其后的第二条只等 15s 就过了。说明卡的是**请求密度**，不是时间窗口。

所以按平台分别计时，同平台两次请求之间补足最小间隔：
B站 8s，抖音/小红书 4s，微博/TikTok 3s，其余 1.5s。单条跑无感，批量档才起作用。
退避档位同时提到 20/60/150。

**不让它撞上，比撞上之后等更久有效。** 再往上加退避意义不大。

### 5. TikTok 失败提示

`@patroxofficial` 那条报 `Unable to extract universal data`，
但同批 `@hankgreen1` 成功——extractor 没坏，是 yt-dlp 每次要现解一道 JS 挑战题，
解不开就失败，**间歇性的**（第二次跑就自己过了）。

不自动降级到 TikWM：那是第三方服务，等于把链接发给别人，
**要不要发是用户的选择，不是默认值**。Codex 设成 opt-in 是对的。
只是让失败提示把这条路和它的代价说出来。

## 三、09-07 上午：接过 Codex 1.2 之后

Codex 1.2 交回时源码/app/校验清单 sha256 三者一致，单一代码线。
它那份「更正交接中的历史结论」有一条是对的：**我把视频号的 ISAAC64
写成了已验证，其实日志只证明了解码验收通过。** 查代码发现问题更深一层。

### 3.1 修的

| 改动 | 说明 |
|---|---|
| `vx_wxchannels.py` 的 `tool` 字段 | 原来无论加不加密都写 `+ ISAAC64`，是溯源信息造假。改成按 `valid` 分支 |
| `ids_from_capture()` | 从抓流的媒体地址（`clientCacheKey`）和 referer 挖平台原生作品 ID / authorId，目录名不再是无意义哈希 |
| OCR ROI 自动放宽 | 默认底部 30% 一无所获时改扫全图，并说明扫的是全图；新增 `--ocr-roi` |
| OCR 失败不再静默 | 缺二进制 / 非零退出 / 输出非 JSON，三种分别打日志 |
| 薄结果判定 | 从「总字数为 0」改成「没有一帧够 4 字」，和 `has_hardsub()` 共用阈值 |
| `--force` 重抽帧 | 原来帧存在就跳过，`--interval` 在重跑时是静默 no-op |
| mtime 不再冒充发布日期 | 只有 `platform == "local"` 才补，否则同一视频从不同入口进会落到两个目录 |
| 薄结果不产出 SRT，并清旧文件 | meta 说「未产出」而磁盘上留着旧的，是自相矛盾的状态 |

### 3.2 让步的

**格式选择器的中间层**：我早上补的「直连不限高」被 Codex 撤掉，理由是不能
静默把 1080p 变成 4K。**按 Codex 的**——我没想到兜底拿到的 4K 在 YouTube 上
必然是 VP9，用户会得到一个又大又打不开的文件还不知道为什么。
坑清单 32 条记的是分歧和裁决，不是某一方的结论，末尾写了「别再翻第三次」。

### OCR 的能力边界（实测结论，别再调）

直接 `visionocr <单帧>` 不带 ROI，对一帧有粗白描边竖排大字「菜包」的画面
返回 `"lines": []`。不是 ROI 问题、不是帧数问题、不是代码丢结果——
**Vision 的检测器对这类字形不响应**。要覆盖得换 PaddleOCR，
但当初选 Vision 就是为了避开 PaddlePaddle 全家桶，不建议为这一类内容翻案。

> 诊断方法值得记住：**绕过自己的代码，直接对单帧跑 `visionocr`**。
> 这一条命令把「ROI 错 / 帧数少 / 代码丢结果 / Vision 认不出」四种可能
> 一次分开。我在流程里来回调了三轮都没定位到，因为四种病在流程输出里长得一样。

## 五、剩下的

1. **MITM 收窄**：实测只命中 `finder.video.qq.com` 和 `v23-3.kwaicdn.com`，
   配置里那五个是推测的。建议改成 `finder.video.qq.com` + `*.kwaicdn.com`
   ——**用通配**，因为 kwaicdn 有多个编号节点，写死 `v23-3` 换节点就抓不到。
   需要先看 `15_check_surge.sh` 输出的 MITM 现状。
2. **ISAAC64 分支**：抓流候选里那条标了「加密媒体」的视频号作品是真实样本，
   但抓流拿不到 decodeKey（只在元宝的 `get_feed_info` 里给），
   得从元宝那条路找一条加密作品才能验。
3. **批量的真实用途**：`vx -f` 至今最大 15 条，而这套东西是为
   「对一个创作者做全量蒸馏」建的。几十上百条时限速退避和节流扛不扛得住，
   只有那时候才知道。

## 六、这一天真正的教训

坑清单从 28 条涨到 50 条，其中超过一半是同一个病根：

> **跳过、失败、和「确实没有」在输出里长得一样。**

29/30/31 选流选错了却没人知道；44 OCR 静默返回空；46 重跑落到新目录；
47 帧没重抽导致两次实验不可比；49/50 判定无效之后照样留下文件。

**改代码之前先问一句：这条路走不通的时候，看得出来吗？**
