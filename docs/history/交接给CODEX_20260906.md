## 2. 我改了什么

### 2.1 truststore 改成可选依赖（`vx.py` 21–31）

**症状**：用户说"打包完的 app 都不能用"。
**原因**：`vx.py` 顶层是裸 `import truststore`，venv 里没装的话
**每一条 vx 命令**都 ImportError，表现就是"什么都不能用"。
**改法**：

```python
try:
    import truststore
    TLS_CONTEXT = truststore.SSLContext(ssl.PROTOCOL_TLS_CLIENT)
    HAS_TRUSTSTORE = True
except Exception:
    TLS_CONTEXT = ssl.create_default_context()
    HAS_TRUSTSTORE = False
```

truststore 只服务于抓流拿到直链之后那几步（要验 Surge 的 MITM CA），
没有理由让它缺席就把整个程序拖死。

**验证状态**：诊断脚本跑过，用户机上 truststore 其实是装着的，
所以这一条不是这次故障的真正根因——但它是个真实的脆弱点，改动保留。

### 2.2 【根因一】YouTube 默认不带 cookie（`vx.py` 74–90）

**症状**：`ERROR: [youtube] hlre2n_3bFM: Requested format is not available`
**原因**：这是我 09-03 自己引入的回归。当时为了让 Vimeo 能过，
我把 `needs_cookies()` 改成对所有站点一律返回 `True`，理由是
"yt-dlp 只把 cookie 发给对应域名，带上没有额外风险"。
**这个推理是对的，结论是错的**——风险点根本不是 cookie 泄漏，
而是 **平台看到登录态会返回不同的内容**。YouTube 带上登录 cookie 之后
只返回 video-only 轨，不给音频轨，`bv*+ba/b` 自然选不出东西。

**改法**：

```python
YOUTUBE_COOKIES = False          # 74 行

def needs_cookies(url):          # 76 行
    if platform_of(url) == "youtube":
        return YOUTUBE_COOKIES
    return True
```

命令行 `--youtube-cookies` 可以显式打开（会员/年龄限制内容需要）。

**验证状态：已实测，对照实验三组**
- A：不带 cookie 解析 → 成功
- B：带 Chrome cookie 解析 → 失败，报 format is not available
- C：`--list-formats` → 清一色 "video only"

### 2.3 通用兜底：任何站点报 format is not available 就去掉 cookie 重试（`vx.py` 174–182）

因为这个陷阱不见得只有 YouTube 有，所以在 `fetch_meta()` 里放了通用兜底：

```python
if "format is not available" in last.lower() and browser and browser != "none":
    log("带 cookie 时平台没给出可用格式，去掉 cookie 重试", "↻")
    r2 = run(ytdlp_base(url, "none") + ["--skip-download", "--dump-single-json", "--no-playlist", url])
    if r2.returncode == 0:
        try:
            return json.loads(r2.stdout), None
        except json.JSONDecodeError:
            pass
```

**验证状态：未实测。** 逻辑上是 2.2 的推广，但没有第二个平台的真实样本
触发过这条分支。**这是留给你的验证点之一。**

### 2.4 【根因二】格式选择器避开 m3u8/HLS

**症状**：解析成功、开始下载，然后 153 个分片全部
`SSL: UNEXPECTED_EOF_WHILE_READING`，整条挂掉。
**原因**：`bv*+ba/b` **只比码率**。YouTube 那条视频里 format 616
（4164k, m3u8, "Premium"）码率高于 format 137（2746k, https），
于是被选中。m3u8 意味着一条视频拆成 153 个短连接，
在用户这台开着 Surge 增强模式的机器上，每片都可能握手失败。
https 单连接即使中途 SSL 抖动，yt-dlp 能续传；分片不能。

**验证状态：已实测。** 改完之后同一条链接选中 `137+251-drc`，
288.86 MiB + 14.47 MiB 合并成 303.5 MB，全流程走完
（FunASR 182 段字级时间戳、99 帧、检测到硬字幕）。

### 2.5 【根因三】限画质 + 限编码（`vx.py` 332–372、1469、1501–1502）

**症状**：修完 2.4 之后，YouTube 又选中 `313+251-drc`。
**原因**：313 是 2160p **VP9**，251 是 **Opus**。协议卡住了，但
分辨率无上限、编码无偏好，于是一路爬到 4K VP9，
再被 `--merge-output-format mp4` 塞进 mp4 容器。

产物是"有效但打不开"：ffmpeg 读得动（所以下游转写抽帧不受影响），
但 **QuickTime、Finder 预览、多数剪辑软件都放不了 VP9-in-MP4**。
而且 4K 对这套流程的下游（ASR 只吃音轨、硬字幕 OCR 1080P 足够）
没有任何增益，只是把体积和 OCR 耗时翻几倍。

**改法**：新增 `build_format_selector()`，三层从严到松，每层都有兜底：

```python
def build_format_selector(max_res=1080):
    https = "[protocol^=http][protocol!*=m3u8]"
    cap = f"[height<=?{max_res}]"
    return (f"bv*{https}{cap}+ba{https}/b{https}{cap}"
            f"/bv*{https}+ba{https}/b{https}"
            f"/bv*+ba/b")
```

- 第一层：https 非分片 **且** 高度不超过 max_res
- 第二层：https 非分片，不限高度（有些平台不报 height）
- 第三层：什么都行（某些平台只有 m3u8，总不能一条都下不了）

`[height<=?1080]` 里的 `?` 是关键：字段缺失时不判否，
否则不报 height 的平台会把整层废掉。

排序同步改成：

```python
"-S", f"proto:https,res:{max_res},vcodec:h264,acodec:m4a,br",
```

协议第一（别再被分片流吸走）→ 分辨率 → 编码（h264/aac 优先于
vp9/av1/opus）→ 码率。

新增命令行开关：

```python
ap.add_argument("--max-res", type=int, default=1080, metavar="N",
                help="画质上限，默认 1080。要原画存档就 --max-res 2160")
```

调用点（1469 行）：`download(url, outdir, br, max_res=getattr(args, "max_res", 1080))`

**验证状态：只实测了一半。**
- ✅ 语法通过，`build_format_selector(1080)` / `(2160)` 输出串已人工核对
- ✅ B站一条实测选中 `30112+30280`（h264 + m4a），正常
- ❌ **YouTube 4K 那条没有复测**——B站本来就只给 h264，验不到限高分支
- ❌ `--max-res 2160` 从没跑过

**这是留给你的最重要的验证点：找一条有 2160p VP9 的 YouTube 视频，
确认现在选中的是 1080p h264 而不是 4K VP9。**
