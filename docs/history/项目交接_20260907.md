## 0. 一句话

把任意平台的一条视频链接，变成一个带元数据、字幕/转写、关键帧的本地目录，
并登记进总表。九个平台已跑通，命令行和 macOS app 两种用法。

**当前状态：管道全部跑通，但从没做过一次真正的"蒸馏"** —— 见第 8 节。

## 1. 怎么用

### 命令行（内核，功能最全）

```bash
vx <链接>                          # 标准档：下载 + 转写 + 抽帧 + 落盘
vx <链接> --download-only          # 只下载，转写和 OCR 事后再补
vx -f links.txt                    # 批量档，逐行读链接，靠 .done 断点续跑
vx <链接> --dual                   # 进正式材料：OCR + ASR 双路互校
vx <本地文件> --as kuaishou        # 本地媒体进库，指定平台
vx <链接> --max-res 2160           # 画质上限，默认 1080（理由见 4.2）
vx <链接> --force                  # 忽略 .done 重跑（不重下媒体、不刷元数据）
vx <链接> --redownload             # 换画质后重下，旧文件挪进 media/_replaced/
vx <链接> --refresh-meta           # 强制重取元数据（限速主要卡在这一步）
```

### app

`/Applications/拾影视频下载器.app`。三档：仅下载 / 下载并转写 / 下载、转写和 OCR。
可选剪贴板收集（默认关，只收支持的平台链接，去重加入队列，不自动下载）。
**app 每条任务独立起内核进程**，所以它自己另有一层父进程平台间隔。

改了源码之后要同步进 app，否则 app 用的还是旧内核：

```bash
bash scripts/18_fix_app.sh          # 诊断 + 同步 + 重新签名
bash scripts/18_fix_app.sh --check  # 只诊断，不改任何东西
```

### 快手 / 视频号（走 Surge 抓流）

```bash
vx-capture start          # 起本地接收端（端口 18787）
# 然后在浏览器里把视频播起来（要点播放，光开页面不发媒体请求）
vx-grab                   # 列候选
vx-grab 3                 # 处理第 3 条
```

**从作品页播，别从推荐流播**——作品页的 referer 里有 authorId，推荐流没有。

## 4. 几个关键设计，改之前先看

### 4.1 文本来源的优先级

官方字幕 > ASR。人工轨 > 自动轨。原声轨 > 译文轨。
译文轨单独存，不覆盖原声轨。

ASR 引擎按语种选：中文 FunASR（paraformer-zh + fsmn-vad + ct-punc），
英文 parakeet-mlx。**语种判定看 `language` 字段 + 标题中文字符占比，
不能看 `available_subs`**——一条英文视频挂 30 种字幕轨是常态。

FunASR 的分句要**自己从字级 `timestamp` 按标点切**，`sentence_info` 不可靠
（实测 143 秒视频只返回 1 段）。

### 4.2 画质：默认 1080，不是省流量

YouTube 的 4K 只有 VP9/AV1，**没有 h264**。`--merge-output-format mp4` 会把
VP9+Opus 塞进 mp4 容器：文件有效、ffmpeg 读得动，但 QuickTime、Finder 预览、
多数剪辑软件都打不开。所以 **1080 是"下下来能直接双击播放"的上限**。

格式选择器两层：`直连+限高` → `任意协议+限高`，排序
`proto:https,res:{max},vcodec:h264,acodec:m4a,br`。
**协议放第一位**是因为 m3u8 会把一条视频拆成上百个分片，
在开着代理的机器上每片都可能握手失败。

### 4.3 YouTube 的 cookie 是个钟摆

同一台机器、同一条链接，几小时内两种表现都出现过：

| 情况 | 报错 |
|---|---|
| 带 cookie | `Requested format is not available`（只给 video-only 轨） |
| 不带 cookie | `Sign in to confirm you're not a bot` |

**静态默认值必然错一半**，所以两个方向都兜：报 format 错就去掉 cookie 重试，
撞机器人校验就强行带上重试。成功那次的姿势经 `_vx_force_cookies` 传给
字幕和下载，否则 `needs_cookies()` 会在下一步把 cookie 又剥掉。

识别串注意 **YouTube 用弯引号 U+2019**，直引号匹配不到，两个都要列。

### 4.4 限速：节流优先于退避

B站的 412 卡的是**请求密度**不是时间窗口。实测批量里第一条 B站
15/45/90 三档退避全用完（150s）仍然 412，紧随其后的第二条只等 15s 就过了。

所以 `throttle()` 按平台分别计时补足最小间隔：B站 8s，抖音/小红书 4s，
微博/TikTok 3s，其余 1.5s。退避提到 20/60/150。
**不让它撞上，比撞上之后等更久有效。**

### 4.5 安全边界（这些是有意为之，别"优化"掉）

- **不生成 `cookies.txt`**，一律用 `--cookies-from-browser` 直读。
  那个文件等于全平台登录态的明文副本。
- **cookie 只发元宝域名**，`vx_wxchannels.py` 里是显式拒绝而非隐式信任；
  不跟随重定向；媒体 URL 必须 `*.qq.com`；decodeKey 校验为 uint64；
  解密后必须过真实 ffmpeg 解码检查。**重构时别弄丢这四条。**
- **TikWM 默认关**。走它等于把链接发给第三方，是用户的选择不是默认值。
- **Surge 配置由脚本在本地读写**，Claude 不读其内容（里面有订阅和密码）。
- **`--redownload` 挪不删**，几百 MB 的东西删了找不回来。

## 6. 已知限制

**Vision OCR 读不了粗描边的美术字。** 直接 `visionocr <单帧>` 不带 ROI，
对一帧有粗白描边竖排大字「菜包」的画面返回 `"lines": []`。
不是 ROI 问题、不是帧数问题、不是代码丢结果——**Vision 的检测器对这类字形不响应**。

- 规整硬字幕（影视剧、口播视频底部那种）→ 有效，`--dual` 留着
- 贴纸式美术字 → 放弃。要覆盖得换 PaddleOCR，但当初选 Vision 就是为了
  避开 PaddlePaddle 全家桶，**不建议为这一类内容翻案**

**小红书的 `xsec_token` 约一小时过期。** 同一条链接过期后取不到，要现复制。

**快手元数据要人工补录。** 抓流拿不到发布时间和播放量，`evidence` 记「待核对」，
正式材料要附一张带系统时间的截图。

**app 不是通用分发包。** ad-hoc 本地签名、未公证、依赖本机 `~/.vx` 环境，
不含 ASR 模型。换台 Mac 要重新走安装脚本。

## 8. 优化建议

按我的判断排序，理由都写了。

### P0 · 停止建设，开始使用

**这套东西一次都没干过它被建出来的那件事。** 项目起点是 `/kol-distillation`
——把一个创作者的全部内容蒸馏成经过验证、可执行的清单。五天全花在建管道上，
蒸馏一次没做过。

而且有个巧合值得利用：剩下那条工程验证「批量从没在几十条规模上跑过」，
和「真正做一次蒸馏」**是同一个动作**。跑一个创作者的全量内容，
既是压力测试也是产出，不用分两次。

缺的是首尾两步：

1. **频道全量目录抓取** —— 给定频道/主页，生成 `links.txt`。
   YouTube 用 `yt-dlp --flat-playlist` 最简单，B站和抖音要另想办法。
2. **蒸馏本身** —— 几十份 `transcript.srt` + `meta.json` 进去，
   一份带出处、可执行、经过交叉验证的清单出来。**这一步才是价值所在**，
   前面全是搬运。

建议选中文创作者（FunASR 那条路验得最透）、有官方字幕的更省事。

### P1 · 收窄 MITM 白名单（安全，五分钟）

现在解密范围是**五个推测的域名**，实测只命中两个：
`finder.video.qq.com`（视频号）和 `v23-3.kwaicdn.com`（快手）。

建议改成 `finder.video.qq.com` + `*.kwaicdn.com`。**用通配**——
kwaicdn 有多个编号节点，八条样本都是 `v23-3` 只因为同一天同一条线路，
换网络或过段时间可能变成别的编号，写死一个会突然抓不到。

**白名单开着不用是纯风险**，被解密的流量越少越好。
改之前先看 `bash scripts/15_check_surge.sh` 输出的 MITM 现状。

### P2 · 批量的健壮性（要等真跑大批量才知道要不要做）

跑几十上百条时可能暴露的：

- 节流参数够不够（现在的值是按 15 条的观察定的）
- 中断之后 `.done` 断点续跑真的接得上吗（从没测过中断）
- 磁盘增长（一条 1080p 长视频 300 MB 起，一个频道几十条就是几十 GB）
- 是否需要"只要字幕不要媒体"的档位——做蒸馏其实不需要留视频

最后一条我觉得价值最高：**加一个 `--text-only`**，取完官方字幕或转写完
就删媒体。做全频道蒸馏时能省掉 90% 的磁盘。

### P3 · 可以做但别急

- **快手元数据补录的半自动化**。referer 里有 authorId，缺的是标题和发布时间。
  可以从作品页 HTML 里抓，但快手网页是 SPA，要么上浏览器自动化要么算了。
- **`vx-relabel`**：事后修改 meta 并同步 index.csv。现在补录只能手改 JSON，
  改完 index.csv 还是旧的。
- **抓流候选的自动清理**。`~/.vx/captures.jsonl` 只增不减，跑久了列表会很长。

### 不建议做

- **继续加平台。** 主线九个够了，剩下的用 yt-dlp 通用兜底试一下，不通就算。
- **打磨 app 界面。** 工具够用了，再美化也不会让你多读到一个视频。
- **为贴纸美术字换 PaddleOCR。** 见第 6 节，权衡过了。

## 10. 维护须知

**改 `vx.py` 之前先读 `HANDOFF.md` 第六节的 50 条坑。** 重新踩一遍代价很高，
里面每一条都是实测撞出来的，不是推测。

改完检查语法：`python3 -m py_compile scripts/src/vx.py`。
`vx` 是软链，改完即时生效不用重装；但 **app 里是拷贝，要跑 `18_fix_app.sh` 同步**。

回归测试在 `scripts/test_*.py`（平台、抓流、GitHub 适配器、下载策略、格式选择）。

### 这个项目最重要的一条经验

坑清单从 28 条涨到 50 条的那一天，超过一半属于同一个病根：

> **跳过、失败、和「确实没有」在输出里长得一样。**

选流选错了却没人知道；OCR 静默返回空；重跑落到新目录；帧没重抽导致两次
实验不可比却被当成对照；判定无效之后照样留下文件。每一个单看都是小 bug，
合起来的效果是**这套东西"跑通"过很多次，其中好几次是假的**。

所以：**改代码之前先问一句，这条路走不通的时候，看得出来吗？**

还有一条配套的：**绕过自己的代码，直接对最小单元跑一次。**
OCR 那个问题我在流程里来回调了三轮 ROI 和帧数都没定位到，
用户跑了一条 `visionocr <单帧>`，十秒钟出结论。
