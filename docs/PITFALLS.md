### 关于 vx 内核

1. **官方字幕优先于 ASR；人工轨优先于自动轨；原声轨优先于译文轨。**
   yt-dlp 的 `--write-subs`（人工）和 `--write-auto-subs`（自动）**输出文件名完全相同**，
   必须分目录下（`subs_manual/` 和 `subs_auto/`）。混下时拿到的是自动轨——
   实测 3Blue1Brown 那条 `sloppily` 被听成 `slapperly`，无大小写标点。
   原声轨优先是因为落盘规范写着「一手可直引」，正文是译文的话这句话就名不副实。

2. **字幕获取必须独立于视频下载**，用 `media/.subs_fetched` 标记。
   媒体文件已在本地时主流程会跳过下载，字幕会跟着一起跳，
   结果白跑一遍 ASR 去转一个本来有官方字幕的视频。

3. **语种判定不能看 `available_subs`。** 一条英文视频挂着 30 种语言的字幕轨是常态，
   里面有 zh 只说明有中文翻译。要看 `language` 字段和标题的中文字符占比。
   实测就是这么把 3Blue1Brown 的英文视频送进 FunASR 的。

4. **FunASR 的时间戳要自己从字级 `timestamp` 按标点切句**，
   别指望 `sentence_info`——实测 funasr 1.4.13 对一条 143 秒视频只返回 1 个元素。
   对齐规则是**中文逐字、英文逐词**（`the` 3 个字符占 1 个 timestamp 项，
   差值验证严丝合缝）。按字符对齐会让时间轴越往后偏得越多。

5. **质量闸门用「最高频字符占比」，不用「不同字符数比例」。**
   后者对英文恒等于 0.00（26 个字母除以几千字符），对正常中文也偏严（0.28 被误判）。
   前者跨语种成立：正常中文最高频的「的」约占 4%，无口播视频里「嗯」占六成。
   阈值：语速 < 0.8 字/秒，或单字符占比 > 0.35。
   **这是保守的启发式不是可靠判据**，命中只降级为「存疑」并提示，不替用户下结论。

6. **元数据必须本地缓存**（`lib/.cache/`）。国内平台限速是常态，重跑转写、
   补抽帧、改参数本来就不需要联网，每次都请求只会白撞 B 站的 412。

7. **cookie 默认对所有站点带**，支持多浏览器按序尝试（默认 `chrome,edge`）。
   原先只对国内平台开是错的划分——yt-dlp 只把 cookie 发给对应域名。
   用 `--cookies-from-browser` 直读，**不生成 cookies.txt**（那文件等同全平台登录态）。

8. **抖音拿不到播放量**，平台不公开，只有点赞/评论/收藏/分享。记 `null` 不记 0。

9. **小红书链接里的 `xsec_token` 会过期**，实测一小时后同一条链接报
   `No video formats found`。批量档不能提前很久备链接清单。

10. **yt-dlp 的 weibo extractor 已失效**（`KeyError('Component_Play_Playinfo')`，
    换 `video.weibo.com` 入口变成 `JSONDecodeError`），且已是最新版，属上游问题。
    绕法：`m.weibo.cn/detail/<mid>` 的 `$render_data`（注意用移动端 UA），
    视频用接口给的 mp4 直链下。`m.weibo.cn/statuses/show` 那个端点现在对未登录返回 HTML。

11. **公众号文章的作者取 `nickname` 不是 `author`**——后者多数文章是空字符串，
    第一版正则匹配到空值后又贪进了后面的 JS，作者字段变成 `"; var author_id =`。

12. **`index.csv` 按 slug 去重写入**，不能纯追加——`--force` 重跑会让同一条出现多次。

13. **目录名缺哪段省哪段**，别硬拼 `unknown_nodate`。

### 关于 yt-dlp 选流（2026-09-06 补，两次「全平台都不能用」的根因都在这里）

29. **YouTube 默认不能带 cookie**（`YOUTUBE_COOKIES = False`，`--youtube-cookies` 才开）。
    带上登录态之后 YouTube 只返回 video-only 轨，`bv*+ba/b` 选不出东西，
    报 `Requested format is not available`。对照实验证过：不带 cookie 成功、
    带 cookie 失败、`--list-formats` 全是 "video only"。
    风险点不是 cookie 泄漏（yt-dlp 只发对应域名），而是**平台看到登录态会返回不同的内容**。
    `fetch_meta()` 里另有通用兜底：任何站点报 format is not available 就去掉 cookie 重试一次。

30. **格式选择器必须先按协议筛，再比码率。** 纯 `bv*+ba/b` 只比码率，
    会选中 m3u8/HLS 的 Premium 轨（例：format 616 比 137 码率高），
    于是一条视频拆成 153 个分片，在代理下每片 `SSL: UNEXPECTED_EOF_WHILE_READING`，整条挂掉。
    现在的选择器是 `bv*[protocol^=http][protocol!*=m3u8]+ba[...]/b[...]/bv*+ba/b`
    配 `-S proto:https,res,br`。单连接 https 即使中途 SSL 抖动，yt-dlp 能续传；分片不能。

31. **只限协议不限画质和编码还不够。** 修完 30 之后 YouTube 又挑中 format 313
    （2160p VP9）。`--merge-output-format mp4` 会把 VP9+Opus 硬塞进 mp4 容器：
    文件本身有效、ffmpeg 读得动，但 QuickTime、Finder 预览、多数剪辑软件都打不开，
    而且 4K 对下游的 ASR 和画面 OCR 没有任何增益，只是把体积和 OCR 耗时翻几倍。
    现在选择器分三层（限高的 https / 不限高的 https / 全兜底），
    排序改成 `proto:https,res:1080,vcodec:h264,acodec:m4a,br`，
    并加了 `--max-res`（默认 1080，要原画存档就 `--max-res 2160`）。

32. **限高兜底层要不要保「直连」——我和 Codex 反复过两次，最后按 Codex 的来。**

    - Claude 09-07 早：补了中间层「直连不限高」，理由是少数视频只有超上限的直连轨
      加不超上限的 m3u8 轨，选中 m3u8 在开着代理的机器上必挂，
      主张**协议可靠性优先于画质上限**。
    - Codex 09-07 晚：撤掉，理由是**不能静默把用户要的 1080p 变成 4K**，
      超限直连与限高 HLS 共存时选限高 HLS，网络失败就明确报错。
    - **裁决：按 Codex 的。** 我的方案有个我当时没想到的副作用——
      兜底拿到的 4K 在 YouTube 上必然是 VP9（见 33 条），
      用户会得到一个又大又打不开的文件，而且不知道为什么。
      Codex 的方案是「明确失败 + 有逃生出口（`--max-res 2160`）」，
      比「静默给个意外结果」好。

    **现在的选择器是两层**：`直连+限高` → `任意协议+限高`。
    **别再翻第三次**——两种都能自圆其说，反复改比选错更糟。

33. **YouTube 的 4K 只有 VP9/AV1，没有 h264。** 所以 `--max-res 2160` 拿到的
    必然是 QuickTime 打不开的 VP9-in-MP4（实测 2160p 选中 `313+140`，
    1080p 选中 `137+140`）。默认 1080 不只是为了省体积，
    **它是"下下来能直接双击播放"的上限**。真要 4K 又要能播，只能下完再转码。

34. **YouTube 会在两种失败之间来回摆，静态默认值必然错一半。**
    同一台机器、同一条链接，09-06 下午带 cookie 报
    `Requested format is not available`（只给 video-only 轨），
    09-07 凌晨不带 cookie 报 `Sign in to confirm you're not a bot`。
    这不是回归，是平台按 IP 信誉动态收紧。
    所以 `needs_cookies()` 的默认值怎么设都会有一半时间是错的，
    正确做法是**两个方向都兜**：
    - 带 cookie 报 format is not available → 去掉 cookie 重试
    - 不带 cookie 撞机器人校验 → `force_cookies=True` 强行带上重试

    成功那次的姿势要跟着走完全程：`_vx_force_cookies` 随元数据传给
    `ensure_subs()` 和 `download()`，否则 `ytdlp_base()` 里的
    `needs_cookies()` 会在下一步把 cookie 又剥掉。
    识别串见 `BOT_CHECK_MARKERS`——**注意 YouTube 用的是弯引号 U+2019，
    直引号匹配不到**，两个都要列。

35. **`--force` 换不掉已有的媒体文件。** 它只忽略 `.done` 标记，
    主流程仍然是「`find_media()` 非空就跳过下载」。所以画质策略一变，
    老目录里那个文件永远换不掉——实测：限高改好之后重跑 `DBpE9WcC11E`，
    拿到的还是昨晚那个 2160p VP9（173.8 MB，QuickTime 打不开）。
    为此加了 `--redownload`：把旧媒体挪进 `media/_replaced/` 再重下，
    **挪而不删**，几百 MB 的东西删了找不回来，由用户自己决定何时清。

36. **`--force` 不等于「重新跑一遍」，别拿它当压力测试。**
    它只忽略 `.done` 标记：元数据照样读 `lib/.cache/`，媒体只要在本地就跳过下载。
    实测 09-07 那次 15 条批量 `--force` 复跑，`ok: 15` 看着漂亮，
    但只有 1 条真的走了网络——B站的 412 退避一次都没触发。
    真要压网络层：`--refresh-meta` 强制重取元数据（限速主要卡在这一步，
    且几乎不耗流量），`--redownload` 才会重下媒体。
    现在 `--force` 遇到已有媒体会打一行提示，免得再误判一次。

37. **B站的 412 卡的是请求密度，不是时间窗口；节流比退避管用。**
    实测 09-07 十五条批量：三条 YouTube 打完紧接两条 B站，
    第一条 B站 15/45/90 三档退避全用完（累计 150s）仍然 412，靠缓存兜底；
    紧随其后的第二条只等 15s 就过了。
    所以加了 `throttle()`：按平台分别计时，同平台两次请求之间补足最小间隔
    （B站 8s，抖音/小红书 4s，微博/TikTok 3s，其余 1.5s），
    单条跑无感，批量档才起作用。退避档位同时提到 20/60/150。
    **再往上加退避意义不大——不让它撞上，比撞上之后等更久有效。**

38. **`meta.json` 的 `tool` 字段不能写死，否则溯源信息是假的。**
    `vx_wxchannels.py` 原来无论媒体有没有加密，都往 `tool` 里写
    `Tencent share API + ISAAC64`。但 ISAAC64 只在 ffprobe 读不出视频流
    （`valid == False`）时才走，未加密的作品根本没进 `decrypt_file()`。
    Codex 09-07 指出「解码验收通过」不等于「走过 ISAAC64」，是对的——
    而且函数里 `decoding` 那个变量本来就是条件化的，只有 `tool` 写死了。
    已改成按 `valid` 分支写。**这个项目的 evidence 分级依赖 meta 如实记录，
    记错来源比记漏更糟。**

    连带结论：**ISAAC64 分支至今没有被真实加密作品验证过。**
    现有两个视频号样本都是「分享接口直接给可播放媒体」这一路。
    要验证得找一条真正返回 `X-encflag=1` 的作品。

39. **抓流救不了加密的视频号，两条路不能互相替代。**
    09-07 首次抓流成功，7 条候选里有一条 `finder.video.qq.com` 被标为
    `[加密媒体：缺少解码信息，不能直接提取]`——这是第一个真实的
    `X-encflag=1` 样本，证明 ISAAC64 分支确实有必要（见 38 条）。
    但 **decodeKey 只在元宝的 `get_feed_info` 接口里给**，
    MITM 抓到的是裸媒体请求，拿不到 key。所以：
    - 视频号 → 只能走元宝解析（`vx_wxchannels.py`）
    - 快手 → 只能走 Surge 抓流（yt-dlp 没有解析器）
    两条路各管各的，别指望抓流能兜底视频号。

40. **MITM 域名可以收窄了（09-07 首次抓流成功后）。**
    实测真正命中的只有两个：`finder.video.qq.com`（视频号）、
    `v23-3.kwaicdn.com`（快手）。原来配置里那五个是**推测的**。
    收窄前先多抓几条确认快手是不是固定用 `v23-3`——
    kwaicdn 有多个编号节点，写死一个可能漏。
    **MITM 白名单开得越宽，被解密的流量越多，能窄就窄。**

41. **抓流档别用占位符填 `--title` / `--author`，宁可不填。**
    09-07 首次跑通快手时用了 `--title '从页面上抄的标题' --author '作者名'`，
    结果目录名就成了 `kuaishou_作者名_grab_xxx`——**占位符被写死进目录名和
    index.csv，事后补录 meta.json 也改不回来**。
    不传这两个参数时目录名会自动省掉那段（`kuaishou_grab_xxx`），
    干净得多，也符合 13 条「缺哪段省哪段」。
    正式材料的做法：先不填跑通，再人工补录 meta.json，
    并按约定附一张带系统时间的截图（抓流拿到的元数据是「待核对」，不是一手）。

42. **抓流拿到的两个串里都有平台原生 ID，媒体地址那个更可靠。**
    原来抓流档的文件名是 `grab_<sha前20位>`，目录名就成了一个跟平台无关的哈希，
    既回不到原页面，也没法跟同一作者的其他作品对上号。两个来源：

    | 来源 | 样例 | 有作品 ID | 有 authorId |
    |---|---|---|---|
    | 媒体地址 | `…&clientCacheKey=3xm4y3b94veigzi_b.mp4` | 总是有 | 没有 |
    | referer | `…/short-video/3xm4y3b94veigzi?authorId=3xhafyhtrk29exg` | 只有从作品页播才有 | 有 |

    `ids_from_capture()` **优先取 clientCacheKey**——从首页/推荐流播时
    referer 只有 `https://www.kuaishou.com/`，但媒体地址里那个一直在。
    实测两条对照，两个来源给出的 ID 完全一致。
    authorId 只有 referer 有，所以**从作品页播仍然更划算**（能多拿作者 ID）。

    > 我第一版只解析 referer，并据此告诉用户「从推荐流播就拿不到 ID」——
    > 错的。信息一直在媒体地址里，只是我没看。
    > 教训：**抓流拿到的每个参数都值得先看一眼再下结论。**

43. **Vision OCR 的默认 ROI 是底部 30%，中文短视频的贴纸大字常常不在那里。**
    Vision 坐标原点在**左下角**，`0,0,1,0.30` 是底部三成（经典字幕条）。
    实测一条快手视频，「菜包」两个大字在从底部往上 31%～41% 处，
    **刚好擦着默认 ROI 出去**，OCR 返回 0 字。
    现在：默认 ROI 一无所获时自动用全图（`0,0,1,1`）重扫一次并说明，
    也可以 `--ocr-roi` 显式指定（显式给了就不再自动放宽）。
    全图会把路牌、商品包装、水印都扫进来，噪声大，所以只作兜底不作默认。

44. **OCR 这条路之前的「跑通」全是假的，因为它静默失败。**
    二进制不存在、进程非零退出、输出不是 JSON、ROI 扫错地方——
    四种情况在结果里长得一模一样，都是 `OCR 字符数：0`，
    而流程照样打印 `✓ 互校完成`。所以它「通过」过好几次，
    一次都没真正识别出东西。现在每种失败都单独打日志，
    缺二进制会直接告诉用户去跑 `04_build_visionocr.sh`。

    > **通用教训：把「没有结果」和「没能取到结果」显示成同一个样子，
    > 等于给自己造了一个永远会通过的测试。** 这一条值得回头检查
    > 项目里其他返回空列表的地方。

45. **OCR 结果薄不薄，看「有没有一帧成句」，不能看「总字数是不是 0」。**
    43 条改完之后再跑，底部 ROI 把**竖排**贴纸大字从中间切断，
    每组只捞到最下面一个字，结果是「袋 / 啵 / 的 / 甜」四个孤立单字。
    总字数不是 0，所以自动放宽没触发——但这四个字和 0 个字一样没用。
    判据改成 `max(单帧字数) < HARDSUB_MIN_CHARS(=4)`，
    和 `has_hardsub()` 共用同一个阈值，**别改成两套**。

46. **文件 mtime 不能冒充发布日期，否则同一条视频会落到两个目录。**
    `process_local()` 原来在没有发布日期时一律补 mtime。给了 `--as <平台>` 时
    mtime 是「我什么时候下的」，不是「它什么时候发的」。
    后果不只是失真：抓流进来的是 `kuaishou_3xm4y3b94veigzi`，
    同一个媒体文件本地重跑进来的是 `kuaishou_20260907_3xm4y3b94veigzi`，
    **「重新处理已有条目」这件事因此永远做不到**——每次重跑都建新目录。
    现在只有 platform == "local" 才补 mtime。

47. **`--force` 原来不重抽帧，于是 `--interval` 在重跑时是静默 no-op。**
    抽帧的条件是 `if not frames`——目录里只要有帧就整段跳过。
    实测同一条视频前后两次 `--dual --interval 2`：一次 9 帧扫出四个字，
    一次 1 帧扫出零个字，**输出里没有任何迹象表明帧根本没重抽**，
    于是我把两次当成同一个实验对比，得出了错的结论。
    帧是派生数据、重抽几乎不花钱，现在 `--force` 会清掉旧帧重抽并打日志。

    > 又是 44 条那个毛病：**跳过和执行长得一样**。
    > 媒体不重下有带宽理由（所以留了 `--redownload`），帧没有任何理由。

48. **Vision 读不了粗描边的美术字——这是能力边界，不是 bug，别再调了。**
    直接对一帧跑 `visionocr <图>`（不带 --roi，扫全图），返回 `"lines": []`。
    那帧画面正中偏下有两个很大的黑体白边竖排字「菜包」，人眼一望即知。
    所以：
    - **规整硬字幕**（影视剧、口播视频底部那种）Vision 有效，这条路留着
    - **贴纸式美术字**（粗描边、竖排、叠在杂乱背景上）Vision 检测不到，放弃

    诊断方法记住：**绕过自己的代码，直接对单帧跑 `visionocr`**。
    这一条命令把「ROI 错 / 帧数少 / 代码丢结果 / Vision 认不出」四种可能
    一次性区分开，比在流程里反复试快得多。

49. **OCR 太薄时不要产出字幕文件。**
    实测日志里出现过相邻两行自相矛盾：
    `! 全图也没扫到更多，这条确实没有成句的画面文字`
    `✓ 硬字幕已另存 transcript_ocr.srt（4 条）`
    ——那四条是「袋 / 啵 / 的 / 甜」四个孤立单字，还顺手把 `primary` 设成了 ocr。
    **那份 SRT 比没有更糟：它看起来像数据，会被下游当成文本用。**
    现在写文件前复用 `_ocr_too_thin()` 再判一次，薄就只在 notes 里记一句。

50. **决定不产出某个输出时，要把上一跑那份删掉。**
    49 条改完之后 meta 里如实写了「未产出硬字幕文件」，
    但 `subs/transcript_ocr.srt` 还是上一跑留下的那份四个单字的垃圾。
    **`--force` 重跑反而制造了自相矛盾的状态**：meta 说没有，磁盘上有。
    凡是「有条件产出」的文件，不产出的那条分支必须显式清理旧版本。

51. **抖音的 `Fresh cookies (not necessarily logged in) are needed` 不是登录问题。**
    报错原文自己就说了「不一定要登录」，要的是**新鲜**。
    实测 2026-09-07：同一条抖音链接 02:20 能解析，18:41 报这个，
    中间代码和账号都没动——是浏览器里的 cookie 放久了失效。
    **解法：在浏览器里打开一次该平台网站、等页面加载完，再重跑。** 实测有效。
    原来这里统一提示「确认登录了该平台」，会把人引到完全没用的方向。
    这类错误提示要按报错原文分支，别归到一个笼统的「cookie 问题」里。

52. **yt-dlp 现在需要 JS 运行时（deno），没有会静默降级。**
    没装时会打一行 WARNING 然后退到 `visionos` 这类精简客户端，
    并提示 `some formats may be missing`。**今天之前所有 YouTube 的格式测试
    （限高、h264 优先、m3u8 规避）都是在降级客户端下做的**，
    拿到的格式表可能本来就不全。`brew install deno` 之后 yt-dlp 自动使用，
    警告消失。这条影响面比看起来大，值得在任何 YouTube 结论前先确认。

53. **续跑逻辑必须区分「成功过」和「失败过」。**
    `21_channel_survey.sh` 第一版把 ERROR 行也加进 done 集合，
    于是重跑**恰好跳过所有需要重试的条目**，而输出看起来一切正常。
    实测：858 条跑完 277 条失败，重跑时那 277 条被当成已完成。
    又是 44 条那个病根，这次长在我自己的续跑代码里。
    现在只把成功行算作完成，且重跑前会重写文件、清掉重复行和 ERROR 行
    （第一轮跑完文件里有 1146 行、288 个 id 重复）。

54. **长任务的进度反馈要按时间报，不能按条数报。**
    每 25 条打一行，快的时候 40 秒一行、慢的时候 4 分钟一行，
    用户看到的是同一个静止画面，会以为卡死了（实测被问了两次）。
    **「在跑」和「卡死」长得一样**——还是同一个病根。
    判断有没有卡住的正确方法：看输出文件的行数和 mtime 有没有在涨。

> 29～54 这一批里超过一半属于同一个病根：**跳过、失败、和"确实没有"
> 在输出里长得一样**。29/30/31 是选流选错了却没人知道，
> 44 是 OCR 静默返回空，46 是重跑落到新目录，47 是帧没重抽，
> 49/50 是判定为无效之后照样留下文件。
> **改代码之前先问一句：这条路走不通的时候，看得出来吗？**

> 29、30、31 是同一类错误：**自测样本长期固定在同三条视频，平台内部的差异从没覆盖到。**
> 下一个接手的人改选流逻辑之前，先把测试清单扩到十条以上、覆盖同平台的不同形态
> （直播回放 / Premium 轨 / 会员内容 / 长视频 / 竖屏短视频）。

### 关于 Surge 抓流

14. **`[MITM]` 段光有 `hostname` 不生效，必须有 `enable = true`。**

15. **同段多行 `hostname` 只认最后一行**，追加域名必须并进已有那一行，
    否则用户原有的 MITM 域名全废。

16. **`%APPEND%` 前缀在新建的 `[MITM]` 段里是多余的**，
    Surge GUI 会把 `%APPEND% *.kwimgs.com` 整串显示成一个主机名。

17. **Surge 的「脚本」和「HTTPS 解密」是 GUI 里的独立总开关**，配置文件改不了。

18. **`vx-capture` 判断死活以端口为准，不能信 PID 文件**——
    起失败的进程会把 PID 文件覆盖成自己那个即将死掉的 pid，
    于是端口上跑着旧进程、文件里记着死 pid，`stop` 杀了个寂寞还报告成功。

19. **`pgrep -x Surge` 匹配不到**（进程名可能带版本号），用 `pgrep -i surge`。

20. **Surge 脚本必须调 `$done({})` 放行原请求**，卡住的话视频播不起来。

### 关于 bash 脚本本身

21. **`$VAR` 后面紧跟中文字符（包括全角空格「　」和全角括号「（」），
    变量名会被吃进去**，配 `set -u` 直接报「未绑定的变量」。
    **变量后跟中文一律写 `${VAR}`。** 这个坑在本项目里踩了三次。

22. **给用户的补丁脚本必须带幂等检查。** 按行插入的补丁重跑一次会插两遍，
    已经发生过一次（用户跑了两遍，代码重复，靠备份救回来的）。

23. 用户的 zsh 没开 `interactive_comments`，粘贴带 `#` 注释的多行命令会报
    `command not found: #`。给命令时要么不带注释，要么让他跑脚本文件。

### 关于外部工具的裁决（都是实测）

24. **lux 出局**：只对 B 站有效且画质上限比 yt-dlp 低一档（480P vs 1080P），
    对抖音解析失败。留作第三层兜底。
25. **BBDown 退备用**：yt-dlp 对 B 站已给到 1080P 和完整元数据。
26. **TikTokDownloader 没装**：抖音 yt-dlp 已覆盖；快手改走 Surge 抓流。
27. **豆包和元宝的网页版都不能解析视频链接**（实测）。那套生态特权只长在各家 App 里。
    抖音 App 内长按视频有「查看视频文稿」，是平台官方产出算一手，但只能人工复制。
28. **硬字幕 OCR 用 macOS Vision 而非 video-subtitle-extractor**——
    后者依赖 PaddlePaddle，在 M 芯片上装配代价高。Vision 实测中英混排一字不差。
    **注意 ROI 模式下 Vision 返回的坐标是相对 ROI 的，不是相对整图。**
